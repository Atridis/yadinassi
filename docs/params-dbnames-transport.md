# PARAMS/DBNames transport slice

This experimental slice has a finite declaration-observation lane (Phase A)
and a separately selected extraction lane (Phase B). Neither claims native
byte equivalence. The following section describes the retained Phase-A lane.
The explicit `--params-transport-observation` lane has report schema 7, capture
schema 8 and exactly 22 staged sources. Default and older lanes remain closed.
The initial workflow command selected this lane. Its triggers, permissions,
pinned image, actions, native roles/users and artifact destinations stay unchanged.

One existing baseline `audit_record_metadata` call is followed by the existing
closed auditor-image inspection. The native marker is checked but its metadata
names are not used to select PARAMS. One reader completes the catalog, then opens
the selected data and BLOB mappings with the same ownership and budget state.
The hardened inspector hashes and reads through the same descriptor and checks
integrity and quiescence again, including when the reader fails.

The finite projection contains the exact ordered six/seven primitive declarations
for FILENAME, CREATION, MODIFIED, ATTRIBUTES, DATASIZE, BINARYDATA and optional
PARTNO, with fixed ASCII case keys and original spelling. Type, case and lock
tokens match `[A-Za-z0-9_]{0,8}`; integer attributes are exact integers 0..65535.
It includes validated data/BLOB logical lengths, a finite format class, and only
the class of table-data logical byte 0: zero, one, other or unavailable. This is
not a measured record boundary. No stride, row, filename, pointer, slack, BLOB
body, AST, raw value or compression result is published. The whole projection
is capped at 2048 bytes; the capture and complete report retain their 12288- and
32768-byte bounds, including the report's trailing newline.

`integer_zero` uniquely identifies a possible future exact integer format value.
Every other format class stops profile pinning until a separately reviewed
finite exact-value capture is authorized. A nonzero integer class is not a value.
Source manifest, reader/policy hashes, nonce/token, platform, baseline origin,
closed postimage size/digest and storage geometry bind every successful capture.
Later lifecycle or any of the four cleanup failures discard successful capture.
Only declaration capture is claimed. Extraction, layout and mapping are not run;
native byte equivalence is not observed and compatibility is not claimed.

Phase A removes all private images. After source review pins one exact supported
profile, phase B must create its own fresh owned image, recheck that profile and
extract from phase B's own frozen baseline auditor postimage. It cannot retain
phase A's image or use a digest generated by the reader as native byte-equivalence
proof. Row codecs, BLOB-chain extraction, decompression and any mapping/content
parser are not enabled by this capture lane.

## Phase B: one reviewed extraction profile

The separate `--params-dbnames-extraction` lane uses report schema 8, capture
schema 9, lane `owned_params_dbnames_extraction_v1` and exactly 24 staged sources.
Its inventory is the 22-file Phase-A set plus the standalone named-file reader
and the separate extraction policy. The default 20-file lane, historical 18-file
inventory, 21-file metadata lane, 23-file row lane and 22-file Phase-A lane retain
their exact memberships and executable validators. Flags are mutually exclusive.
The reviewed workflow selects Phase B explicitly; triggers, permissions, image,
roles/users, native calls and artifact destinations are not expanded.

Phase A accepted finite declarations from
[run 40191179524](https://github.com/Atridis/yadinassi/actions/runs/40191179524),
head `16b2693bdafdadad45127ff87182473cb5dbdde3`. That is historical evidence
bound to those exact Phase-A source hashes. Adding this route changes shared
source hashes and does not rebind the old run to new source. Phase A retained no
raw image. Phase B runs a fresh ordinary owned lifecycle and rechecks its exact
profile against its own frozen auditor postimage before extracting anything.

Profile `params_dbnames_8380_8192_v1` admits only these complete ordered tuples:

- `(FILENAME, NVC, 0, 128, 0, CI)`
- `(CREATION, DT, 0, 0, 0, CS)`
- `(MODIFIED, DT, 0, 0, 0, CS)`
- `(ATTRIBUTES, N, 0, 5, 0, CS)`
- `(DATASIZE, N, 0, 20, 0, CS)`
- `(BINARYDATA, I, 0, 0, 0, CS)`
- `(PARTNO, N, 0, 10, 0, CS)`

Recordlock is exactly string `0`; the format discriminator is exact integer zero
with unknown semantics. A single status byte and declaration-order widths yield
301 bytes: offsets `1,259,266,273,276,287,295`, widths `258,7,7,3,11,8,6`.
No hidden version or alternate profile is admitted. Complete stride divisibility,
reserved marker 1 and active marker 0 are required; nonreserved free slots fail.
A full bounded scan must find exactly one ASCII-case-insensitive DBNames row.
There is no fixed native row count, expected payload digest or layout search.

The filename codec is bounded strict UTF-16LE with a u16 length prefix. Dates and
attributes remain opaque. Selected N(20,0)/N(10,0) values require sign nibble 1,
decimal digits and unused low padding nibble 0. PARTNO must be zero, DATASIZE
positive and equal to the u32 little-endian BINARYDATA reference length. Only the
selected table's own BLOB chain is read, sharing catalog ownership and cumulative
budgets. Its chain length must match exactly; one bounded raw-DEFLATE stream must
end without truncation, trailing data, wrapper fallback or recursive decoding.
This is a source-justified, falsifiable admission hypothesis, not a general 1C
file-container specification or a claim that Phase A observed record boundaries.

The policy calls the actual standalone `read_dbnames` using independently literal
profile declarations, not a descriptor echo or native metadata names. The
reader is isolated with its exact catalog sibling and stdlib, never by importing
`yadinassi.__init__` or Interpreter. Limits remain 4096 slots, 4096 record bytes,
1 MiB packed, 8 MiB plain, 8192 chain visits and 4096 inflate calls, with existing
catalog limits and the outer isolated-process deadline also enforced.

Only target/profile identifiers, an independently predeclared canonical profile
recipe SHA-256, packed/plain counts and SHA-256 digests are public. The recipe
pins exact declarations, lock/format, stride/placements and versioned framing
and codec rules. The capture additionally binds catalog-reader, extractor,
policy and complete source-manifest hashes, nonce/token, platform, origin and
actual closed-postimage digest/size. Payloads, rows, other filenames, ASTs, paths,
addresses and arbitrary error text are not projected.

Success is only `extraction_observed` for that exact owned image. Mapping remains
`not_run`, native byte equivalence `not_observed` and compatibility `not_claimed`.
The native API does not expose DBNames content, so the extractor's own digest is
not an independent expected digest. All 13 stages, 11 snapshots, five comparisons
and four cleanup gates remain mandatory; any later failure discards successful
extraction. Classified failures are finite and retained only after cleanup.

The complete maximal public-report proof is 31435/32768 bytes including newline
and the full 12288-byte capture cap; margin is 1333 bytes. The full 1024-byte
projection cap yields a 1951-byte capture bound. The accurate standard runtime
provenance gains one source (58 to 59); its full wire/pretty-report envelope
remains 8043/8192 and 32228/32768 without omitting any runtime source or raising
caps. These are offline serializer bounds, not native extraction evidence.
