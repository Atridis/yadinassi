`4fd20bb1f93d582369568212461508a471d467cf`. The preparation sections below record

positive-code readers retain their behavior.

[Official1C guidance](https://1c-dn.com/library/length_of_configuration_object_codes_and_numbers/)

DescriptionLength0/8, Payload variableString32→64 and Amount Number9,2. No

remain; the closed transform removes Code assignment and K1 equality only.
Description assignments are absent in the zero-description case. Designer/native
metadata rejection is a finite acquisition failure, not license to replace a case.

Exact original template SHA256 pins and transform inverses protect existing
routes. A private observer tries ONLY Code property access inside its exception
boundary. Availability is absent (no row), unavailable, string, number or other.
Only supported bounded scalar values are retained privately; no arbitrary-value
conversion or exception description is used. UUID, metadata and enabled
Description readback remain independent controls. Actual values are never seed
expectations or physical reader selectors.

The standalone physical observer admits generic catalog/CONFIG/PARAMS in one
owned lifetime. It independently joins CONFIG UUIDs to DBNames without forging a
positive-code compiler input. Its sole hypothesis omits_CODE and derives optional
_DESCRIPTION width from CONFIG, followed by the two attributes. Valid unexpected
layouts remain unresolved observations without row decoding. Matched layouts
use the existing strict primitive decoder and UUID projection, one active row,
no freed DATA slots, shared ownership and cumulative budgets. No graph escapes.

The original standalone stage did not register native/runtime integration. The
closed integrated lane below now supplies its own mapped-core policy, unique
schemas, source closure and bounded transport gates.
Existing schema2/3 and numeric witness routes, templates and production files are
unchanged in the original standalone preparation; integrated shared-runner
extensions are closed opt-ins and preserve unselected rendering behavior.

Private raw witness cap2048 includes BOM, exact fields and duplicate-key rejection;
actualCode and Description each have128 UTF16-unit bounds (number spelling80).
Public comparison exports finite availability, metadata/UUID/Description verdicts,
counts and descriptor/witness hashes only. No raw values or descriptors escape.
Any later runtime feature requires genuine descriptor/readback evidence and its
own fresh public-reader parity; Code property availability alone proves neither.

### Bounded post-bootstrap syntax observation

If a stopped bootstrap has a valid bootstrap marker and client-before-call
marker, but no server-entry marker, the zero-only lane may run one read-only
Designer `/CheckConfig -ThickClientManagedApplication -Server` check. These
switches select managed thick-client and server-emulation syntax checks
([platform command-line reference](https://1c-dn.com/library/tutorials/1c_enterprise_administrator_guide_file_mode_8_3_27/), section 7.4.5).
The original timeout and failure context remain authoritative. The existing
command timeout, global deadline, process census and filesystem/log budgets
are unchanged. Absence of a frontier marker does not prove why execution stopped.

Only the bounded result code, diagnostic state, log state and up to eight
unique module/line/column/category tuples are exported. Module names are mapped
to fixed `server`, `client`, `session`, or `other`; unknown modules lose their
coordinates. No source text, symbol names, paths or raw log lines are published.
Oversized or unstable logs are unavailable, not truncated into trusted input.
Unknown output, no recognized issues, or even result code zero does not establish
that bootstrap succeeded, that compilation caused the timeout, or that native
CodeLength0 behavior has been measured. This remains a failed report with no
measurement or snapshots; runtime support stays gated on actual native evidence.

The first syntax diagnostic (run 41180979544, commit `a4a70aba`) found
undefined symbols at generated server lines 642 and 644: the observation hook
incorrectly treated `ТипКодаСправочника` as a global enumeration. Metadata
property enumerations are accessed through `Метаданные.СвойстваОбъектов`
([official metadata API guidance](https://its.1c.ru/db/content/metod8dev/src/developers/platform/metod/other/i8102318.htm)).
The correction adds that namespace to the two comparisons; the observed native
`Каталог.ТипКода`, strict witness policy, and runtime guard remain unchanged.
Native reruns, not this source correction, determine whether measurement works.

### Public physical and typed reader admission

The public offline `read_catalog_rows` reader now admits only the measured
String CodeLength0 shapes: DescriptionLength0 or8, Payload length32 or64,
and Amount Number9,2. Catalog/attribute names, UUIDs and physical DBNames IDs
remain dynamically bound. Its physical result has no `_CODE` field; the typed
view projects reference UUIDs from the corresponding six- or seven-field
layout. This does not implement logical BSL `Code` or a catalog manager API.

The separate `catalog-zero-code-rows-v1` native route compares the actual
public typed readback against the native UUID, Description and metadata in
created, updated and applied states. The adapter calls the public reader once
per state with one bounded graph lifetime. Its schema68 report requires the
public-readback wrapper, schema69 capture and43-source manifest; a private
physical observation alone cannot establish public reader parity. The
schema70 aggregate binds both independently nonce-bound cases.

`code_is_empty` is a required independent finite observation in this new route,
not a success expectation or a synthesized return value. Original schema65
measurement reports retain their historical interpretation. Native acceptance
of the new public reader route is pending; the earlier acquisition is evidence
for physical shape, not proof that this new route has run.
