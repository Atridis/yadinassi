# Native fixture evidence and replay

The six environment fields are recorded in
[integrational_tests/meta.md](../integrational_tests/meta.md). Checkpoint evidence,
coverage maps and timezone replay details are kept here separately. The dated
sections record the progression of the evidence; later checkpoints supersede
earlier pending statuses.

## Separate automated Linux capture

[The isolated six-scenario workflow](native-1c-full-regression.md) creates a fresh
Linux/UTC native capture and compares its exact bytes with a separate interpreter
run. Only finite summaries/hashes are public; capture bytes and native logs are
not uploaded. This does not replace the owner-confirmed Windows fixtures below.
A bootstrap/simple-EPF success alone does not establish six-scenario parity.

Owner-confirmed `Get-TimeZone` output for the XML checkpoint run:

- Id: `Central European Standard Time`
- DisplayName: `(UTC+01:00) Варшава, Загреб, Сараево, Скопье`
- StandardName: `Центральноевропейский (зима)`
- DaylightName: `Центральноевропейский (лето)`
- BaseUtcOffset: `01:00:00`
- SupportsDaylightSavingTime: `True`

The exact Windows identifier is **Central European Standard Time**, not
Central Europe Standard Time. Unicode CLDR maps its global (`001`) and Polish
(`PL`) entries to `Europe/Warsaw`:
[official Windows timezone mapping](https://github.com/unicode-org/cldr/blob/release-48/common/supplemental/windowsZones.xml).
This is the replay mapping for this fixture, not a claim that Windows and IANA
historical rules are identical at every date. A fixed `+01:00` offset is not an
adequate replacement for this seasonal timezone. The production interpreter's
host-local policy is separate from the recorded test environment.

Fixture replay uses `YADINASSI_TIMEZONE=Europe/Warsaw` and bundled
`tzdata==2026.5` (IANA `2026e`). This changes only the execution environment;
all output bytes remain compared without timezone normalization.

  `НоваяТаблицаПробы`. After-state and scenario-specific Extra remain independent.

#### Output grammar and readability

The original `table.<label>: [` header and closing `]` remain. Structured fields
are printed on separate lines with a dot path (`Table.Count`, `Nested.Write`).
Arrays preserve element order and use semicolon delimiters; nested structures
retain explicitly encoded keys. Scalar values use their native internal scalar
representation. Before printing a scalar representation, backslash is doubled,
then CR/LF/TAB become `\r`, `\n`, `\t`. Native quoted-string delimiters remain,
so embedded delimiters, quotes, literal escape sequences, Unicode surrogate
escapes and actual newlines are distinguishable. Field paths come only from
fixed test-owned field names, not arbitrary input strings.

including the unchanged 1,451-line prefix. It matches the local replay in full.

### Observed sorting contract and boundaries

Both methods are procedures. Missing or explicit Undefined direction selects
ascending order; Asc/Возр and Desc/Убыв are the only accepted explicit values.
Number 0/1, String, Boolean, Null and a foreign enum are rejected without
reordering. Extra arguments and procedure-as-expression calls also error.
IDs, live item identity, findability, fields and Check flags survive sorting.
Equal keys retain their observed order in both directions; repeated sort is
consistent in the supplied cases. This does not establish an arbitrary native
large-tie sorting algorithm.

The two string contracts differ. SortByValue ignores case and trailing ASCII
spaces. SortByPresentation uses the stored Presentation exactly, including
empty strings: it distinguishes case and trailing spaces, with lowercase before
uppercase in the ascending evidence. The pinned official UCA 6.0 DUCET fits
both supplied Unicode orders when respectively using primary/secondary versus
full keys. This is a bounded empirical fit, not proof that 1C uses UCA6, not a
locale-general claim, and not permission to change existing StrCompare/UCA10
or ValueTable.Sort behavior.

The observed scalar order is Undefined < Null < Boolean < Number < String < Date.
Separate empty-object observations establish Array < Structure with stable
ties; nonempty objects remain unsupported; separate type observations establish Type(String) < Type(Number); separate
enum observations establish SortDirection.Asc < Desc. Cross-family mixes and
other Type/enum identities remain unsupported, rather than guessing a global
native object order. Resource limits and the accepted text repertoire are
listed with the implementation in `features.md`.

The enum value and its type use the native GUID
`8acd280e-c29c-4543-8be7-7f78cad52c06`, ordinals 0 and 1. The owner independently
read back both value streams and the type stream. Namespace presentation and
iteration Asc then Desc are observed; namespace TypeOf and namespace codecs are
not, so no namespace type/GUID is invented. UI, CompareValues, pictures, typed
constraints and active-iteration mutation remain outside this slice.
