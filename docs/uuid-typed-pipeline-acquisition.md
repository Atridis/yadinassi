# UUID в типизированных коллекциях: отдельное измерение

Это acquisition-only пакет из 16 групп. Поддержка runtime ещё не расширена;
наблюдений новой реальной 1С пока нет. `_query_reference`, authority и codecs
ссылок БД, transport, async/reuse capture, смешанные дескрипторы и порядок UUID
не изменяются. Историческая scalar UUID evidence остаётся без изменений.

## Группы

1. Копирование singleton TypeDescription и ContainsType/Types.
2. Singleton TypeDescription из массива Type.
3. Типизированная колонка ValueTable и значение новой строки.
4. Присваивание фиксированного UUID и сравнение с независимо созданным равным.
5. Независимые присваивания канонической String и Undefined: отказ и readback
   фиксируются отдельно; поведение не выводится из AdjustValue.
6. Table.Copy: тип колонки, значение и количество строк.
7. UnloadColumn/LoadColumn: фиксированное и нулевое значения.
8. FillValues двух строк UUID.
9. Find/FindRows по равному UUID; пустой результат не превращается в ошибку observer.
10. FindRows после добавления индекса, без утверждений об упорядочивании.
11. Типизированное дерево: значение по умолчанию родителя и UUID дочерней строки.
12. Tree.Copy: тип колонки и оба уровня. CopyColumns к дереву не применяется.
13. Внутренний writer и независимое чтение Array/Structure с UUID.
14. Внутренний writer и чтение Map/FixedMap с UUID-ключами и значениями.
15. ValueStorage с вложенными Array/Structure UUID.
16. Обратное чтение UUID Type-record; scalar writer уже наблюдался ранее.

Все UUID заданы исходником: нулевой и `11111111-2222-4333-8444-555555555555`.
Случайные UUID, пользовательские данные и внешние файлы не читаются.
Raw internal format разрешён только для этих собственных значений: до 2048
символов, отдельно от проекции типа/значения после чтения. Отказ reader сохраняет
уже полученный writer. Никакой ожидаемый ответ не генерируется из writer.

## Границы acquisition

Используется существующая схема отдельного owned EPF на неизменённой disposable
baseline конфигурации: никаких application/session hooks, common modules или
новых ролей. Точные sources/inputs/hash, nonce, entered/completed markers,
process census, контейнерные ограничения и cleanup сохранены из ранее
проверенной scalar acquisition lane. Не выполняется ручной replay для допуска.

Каждая измеряемая операция имеет отдельную границу отказа `R:action`;
codec writer/reader используют `R:write` и `R:read`. Setup и observer ошибки
попадают в отдельную ограниченную диагностику и запрещают принятие acquisition.
`S:` означает только наблюдение, не доказательство parity. Канал требует ровно
16 упорядоченных записей, ограниченных по размеру; лишние сообщения запрещены.

Будущий workflow допускает только PR из `codex/uuid-typed-pipeline` в main
того же репозитория и проверенного владельца. Checkpoint-ветки не запускают lane;
workflow_dispatch/push/pull_request_target отсутствуют.

Setup использует ранее измеренное имя дескриптора `УникальныйИдентификатор`;
английский alias дескриптора не является частью нового измерения. Одна запись
ограничена 4096 символами; общие пределы вывода и host transport не увеличены.
