# Native-калибровка профиля компиляции модулей

Пакет только собирает наблюдения Linux 1С 8.3.27.1508 в управляемом файловом режиме. Он не включает реализацию нового профиля yadinassi и не заявляет соответствие runtime.

Runtime-профили уже реализованы отдельно в #318 (`a29a8372`): явный профиль передаётся в модули конфигурации и формы. Этот пакет не дублирует runtime, а должен независимо измерить нативное поведение для его калибровки. На 15 ноября исходный CheckConfig завершился неуспешно при совпадении всех пяти загруженных BSL; CP1–CP16 не получены, parity не доказана. Сохраняем исходный неуспешный результат, обновление диагностики не переобозначает его успешным.

Собственная временная конфигурация содержит три неглобальных общих модуля: ClientProbe (клиент), ServerProbe (сервер, ServerCall), DualProbe (клиент и сервер), все DontUse. Единственный параметр сеанса CPState имеет тип String. Новых ролей нет. Только для собственного CPState добавлены Get/Set, необходимые для чтения и установки параметра; базовые права и default-флаги неизменны. Права сверяются канонически после DumpConfigToFiles без игнорирования дополнительных разрешений. Требование доступа: https://kb.1ci.com/1C_Enterprise_Platform/Guides/Developer_Guides/1C_Enterprise_Development_Standards/Creating_and_modifying_metadata_objects/Configuration_operation_arrangement/Session_parameters/ . Это исправление подготовки; прохождение CP2 ещё должно быть подтверждено нативным прогоном.

До добавления исходников адаптер проверяет исходную синтетическую конфигурацию, сохранённые bootstrap/verify markers, отсутствие control.json и точные отрендеренные application/session модули. Код контроля пользователей и защиты сохраняется. Измерительные вставки возможны только при единственном точном anchor; отсутствующий или дублированный anchor означает отказ.

В SessionParametersSetting вставляется запись наблюдаемой RU/EN маски в CPState. В application startup инициализируется CPStartup и находится намеренно исключённое условие Client And Not Client. Дополнительные функции содержат исходные директивы, а не таблицу предполагаемых ответов.

## Шестнадцать групп

1. RU/EN desktop маски application module.
2. Четыре маски session module при запуске: desktop EN/RU и mobile EN/RU.
3. RU/EN desktop маски client-only common module.
4. RU/EN desktop маски server-only common module.
5. RU/EN desktop маски dual common module с клиента.
6. RU/EN desktop маски dual common module через ServerProbe.
7. Доступность guarded ClientExport из клиента.
8. Доступность guarded ServerExport из клиента.
9. Доступность обоих guarded экспортов из сервера.
10. Четыре mobile маски dual common module: EN/RU с клиента и EN/RU через сервер.
11. MobileAppClient/MobileAppServer в application, EN.
12. МобильноеПриложениеКлиент/МобильноеПриложениеСервер в application, RU.
13. Обе mobile маски client-only common module.
14. Обе mobile маски server-only common module.
15. Отсутствие побочного эффекта исключённой startup ветви.
16. Недоступность исключённого экспорта, во втором реальном client event.

Desktop биты в порядке: Client, Server, AtClient, AtServer, ThickClientManagedApplication, ThickClientOrdinaryApplication, ThinClient, WebClient, ExternalConnection. Mobile биты: MobileAppClient, MobileAppServer. Возможность компиляции не предоставляет право вызова на другой стороне.

CP07/08/09/16 используют динамический вызов и возвращают 99 при наблюдаемом отказе, без выгрузки текста ошибки. Остальные ошибки не превращаются в успешное наблюдение: внешний guard пишет error marker, host отклоняет пакет. Наружу допускаются только CP1..CP16, целые коды 0..999 и до четырёх компонентов; никаких UUID, путей или ошибок. Исходный nonce находится только в частном marker; source/module/prepare hashes, prefix первого события, ownership, census и cleanup проверяются исходным guard-механизмом.

MobileClient/MobileStandaloneServer, thin/web/client-server/external режимы и новые runtime API не включены. Шаблон workflow закреплён за отдельной веткой; до независимого review, уведомления о числе проверок и разрешённого запуска никакие CI/native прогоны не выполняются.

Официальные описания: https://1c-dn.com/library/preprocessor_instructions/ и https://1c-dn.com/library/using_compilation_directives/ . Общие описания не заменяют измерения конкретной версии и вида модуля.

При отказе ENTERPRISE отчёт сохраняет проверенную классификацию процессов и
закрытую диагностическую проекцию собственного `enterprise.log`: категория,
известный модуль bootstrap, ограниченный номер строки и идентификатор из
существующего разрешённого набора. Текст ошибки, пути, неизвестные имена и
контекст не публикуются. Диагностика знает только именованные модули собственного пакета и ограниченные номера строк, включая добавленные функции. Неизвестные имена и неоднозначные позиции не публикуются.
Отсутствующий, нерегулярный, символьный или слишком большой файл даёт только
`evidence_invalid`. Диагностика не влияет на допуск успешного измерения.

## Однократная проверка загруженного исходника и компиляции

Перед ENTERPRISE выполняется отдельная выгрузка в собственный новый каталог.
Сравниваются только пять известных BSL-модулей (application, session, три common),
после удаления BOM и нормализации CRLF. Остальной XML не сравнивается; Rights XML дополнительно сверяется целиком канонически, без удаления прав или default-флагов. Наружу выходят
только пять записей с SHA-256 и флагом совпадения; исходники не экспортируются.
Не совпавший или недоступный модуль запрещает дальнейший запуск.

Затем вызывается `/CheckConfig -ThickClientManagedApplication` со свежими
`/Out` и `/DumpResult`. Этот флаг документирован для синтаксической проверки
толстого управляемого клиента в файловом режиме в [руководстве 8.3.27,
«Configuration and extension checks»](https://1c-dn.com/library/tutorials/1c_enterprise_administrator_guide_file_mode_8_3_27/).
Проверки thin/web/server/mobile не добавляются. Ненулевой/невалидный результат
или неуспешный процесс запрещает ENTERPRISE. Каждый процесс сохраняет прежний
120-секундный предел и проверку отсутствия оставшихся процессов.

Отчёт сохраняет результаты обоих этапов даже при прежнем отказе ENTERPRISE.
Категория ошибки `unknown` не становится успешным допуском: она лишь означает,
что закрытый классификатор не распознал текст. Проверка компиляции и совпадение
исходников сами по себе не доказывают выполнение CP1–CP16 или runtime parity.

### Повторная диагностика 15 ноября

На head `c7ba464e` run `43703624824` снова остановился на CheckConfig:
все пять загруженных BSL совпали, результат nonzero, ENTERPRISE не начался.
Artifact `14157850057`, ZIP SHA-256
`40582a2fd484cbc4e8e544800f42e354a4f60914362c13e5fe86c3f3d8cb27b3`, CRC проверен.
Это не успешное измерение. Следующий диагностический вариант читает также
фиксированный собственный `check-console.log` (не более 64 KiB) через тот же
secure reader. Наружу по-прежнему выходит только конечная закрытая проекция;
конфликтующие категории не выбираются произвольно, а дают conflicting_evidence.
Raw console и native logs не публикуются. Проверка не запускается повторно,
пока согласованное окно 1С занято #302.

### Адресный сигнал для оставшегося unknown

Run `43709743967` на `3276ee9c` повторил CheckConfig nonzero, все пять hashes
совпали, `/Out` вместе с console всё ещё дали `unknown`. Artifact `14159822256`
сохранён и проверен (ZIP SHA-256
`8a817ae00e944c1c0dbc68edae14f12e6a578a956202c65323d3566f2413608e`).
Не предполагаем конкретную ошибку BSL. Следующий диагностический сигнал различает
отсутствующий/пустой/валидный/невалидный собственный журнал, BOM и наличие NUL.
Он также сохраняет только уже проверенный конечный словарь токенов из общего
sanitizer, максимум 64 токена на журнал; неизвестные строки и значения не
выводятся. Это поможет отличить проблему кодировки/пустого вывода от ошибки,
которой нет в словаре категорий. Диагностика не меняет CheckConfig/ENTERPRISE
admission, security, исходный BSL и не служит доказательством parity.

### Исправление размера диагностического отчёта

Run `43716143460` (`d153eb6f`) завершился `export_failed` при передаче отчёта,
а не новым измерением CheckConfig. Artifact `14162791295` SHA-256
`9e1d7d656aad29f65044edccfdcf79243cadafab211d56fe9e3ea122372594f4` проверен.
Ошибка воспроизведена offline: исходный manifest вместе с пустыми новыми
диагностическими полями занимает 8219 байт, больше прежнего предела 8192.
Для собственного compilation-profile wire установлен согласованный предел
16384 байта на запись и оба чтения. Общий full-suite предел 8192, лимиты native
процессов, исходников и native admission не изменены. Тест проверяет реальный
manifest с максимальными finite токенами, write/read roundtrip и отказ overflow.

### Результат проверки журналов

Run `43722273795` (`aa0261ef`) уже сохранил настоящий CheckConfig failure:
оба журнала присутствуют, `/Out` UTF-8 BOM, NUL отсутствуют, категория неизвестна.
Отсутствующий/пустой вывод и UTF-16 с NUL не подтверждены. Artifact `14165315322`
SHA-256 `46d0320e9de9b6347d94ac5bfec3a0c1b689be69bd8f5957338fe6c1899673da`
