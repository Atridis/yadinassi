# Асинхронное ядро языка

Поддерживаются клиентские `Асинх Функция` / `Async Function`,
`Асинх Процедура` / `Async Procedure`, `Ждать` / `Await` и тип
`Обещание` / `Promise`. Корневой standalone-код остаётся клиентским.
Это исполняемое ядро с приостановкой и возобновлением кадров, а не синхронная
обёртка результата. Семейства асинхронных API файлов, сети и интерфейса не добавлены.

```bsl
Асинх Функция ЗначениеПозже(Параметр)
    Возврат Ждать Параметр;
КонецФункции

Асинх Процедура Основная()
    ОбещаниеРезультата = ЗначениеПозже(17);
    Сообщить(Ждать ОбещаниеРезультата);
КонецПроцедуры

Основная();
```

## Исполнение

Вызов начинает выполнять тело сразу, до первого `Ждать` или завершения.
Функция возвращает обещание; процедура не возвращает значение. Даже ожидание
готового обещания или скаляра сохраняет кадр и передаёт управление вызывающему
коду. Возобновления обслуживаются одной FIFO-очередью, без потоков Python и без
одновременного выполнения фрагментов BSL. Обычные вызовы не прокручивают очередь.
Внешняя граница `execute` выполняет готовые продолжения до опустошения очереди.

Число, `Неопределено` и `Null` после `Ждать` сохраняются. Повторное ожидание
обещания возвращает тот же результат или повторно возбуждает его ошибку.
Возвращённое асинхронной функцией обещание усваивается внешним обещанием:
ожидание внешнего получает конечное значение. Все параметры асинхронных
подпрограмм передаются как `Знач`, даже без этого ключевого слова. Переприсваивание
параметра не меняет переменную вызывающего кода; изменение переданного массива
остаётся видимым, поскольку передача по значению не означает глубокое копирование.

Локальные переменные, промежуточные результаты выражений, циклы и обработчики
ошибок сохраняются отдельно для каждого приостановленного задания. Переменные
модуля и экземпляр `ЭтотОбъект` остаются общими для вызовов одного модуля.
Синхронные вызовы и импорты используют текущий динамический контекст задания.
Точность Decimal и профиль native target восстанавливаются на каждой активации.

Ошибки тела асинхронной функции сохраняются в обещании, а не попадают в
`Попытка` вокруг одного вызова. Их перехватывают вокруг `Ждать`. Поля расширенной
ошибки не заменяются общим сообщением. Ошибки вычисления фактических аргументов
и проверки вызова остаются ошибками вызывающего кода. Необработанная ошибка
асинхронной процедуры поступает в отдельный host-канал и выдаётся внешней
границей исполнения, не окружающей процедуру BSL-попыткой. Интерфейс платформенного
показа ошибок не эмулируется.

## Границы и embedding

- `Ждать` разрешён только внутри клиентской асинхронной подпрограммы.
- Асинхронные серверные подпрограммы и перенос обещаний на сервер запрещены.
- `Вычислить` / `Выполнить` не наследуют разрешение на непосредственный `Ждать`
  в строке. Вызов асинхронной функции из динамического кода может вернуть обещание.
- `Ждать` имеет приоритет унарного оператора; для составного операнда используются
  скобки. Полный нативный контракт приоритетов ещё не измерен.
- У обещания нет BSL-конструктора, доступных полей, методов или функции разрешения.
  Строковое представление и сериализация обещаний не поддерживаются.
- `Interpreter.pending_promises` отличает блокировку от завершения;
  `Interpreter.run_until_idle()` обслуживает готовые продолжения. `ensure_complete()`
  отклоняет незавершённый lifecycle, `close()` освобождает приостановленные кадры;
  CLI вызывает их перед успешным завершением и при выходе соответственно. Внутренние
  host-controlled promises используются тестами и не являются новым BSL API.
- Планировщик ограничивает один проход 100000 возобновлениями. Это ограничение
  Yadinassi, не платформы. Оно не прерывает бесконечный код без `Ждать`.
- Ожидание нерешённого обещания без готовых продолжений не считается успешным
  завершением задания. Закрытие/reset отменяет оставшиеся кадры в их контекстах.
- Обещания другого планировщика отклоняются; очередь нельзя прокручивать вложенно.

## Подтверждение и ограничения доказательств

Восемь неизменённых language-only case bodies сопоставлены с принятыми данными
реальной Linux 1С 8.3.27.1508, толстый управляемый клиент файловой базы:
run `39964367396`, commit `5eaa21bb292498a45886f746fb54cc730140ac12`.
Все восемь точных трасс, типизированные значения и структурированные ошибки
повторяются в `tests/test_async_native_observations.py`. Fixtures содержат
provenance и отдельные хеши тела и полного нативного модуля. Это повторное
сопоставление уже полученных данных, не новый нативный запуск.

Подтверждены eager-вызов, порядок изученных ожиданий, повторное ожидание,
скалярные операнды, усвоение внутреннего обещания, значения параметров,
обработка отклонения и смешанные RU/EN ключевые слова. Нативные ошибки сохраняют
измеренные description/code/additional/category/cause. Точные платформенные пути,
строки и private descriptors не переносятся в минимальный standalone wrapper.

Тесты настоящего pending/resume с управляемым host-сигналом проверяют механизм
интерпретатора, но не заменяют нативное доказательство внешнего асинхронного API.
Полная семантика динамического `Ждать`, всех приоритетов, наследования диагностики
между независимыми заданиями и платформенного необработанного procedure-error
остаётся вне нативно подтверждённого среза. Конечные измерения одной Linux-сборки
не являются универсальной спецификацией планировщика Windows/web/mobile.

Исторические функции/коллекции/значения/числа/даты не переписаны; новый fixture
является отдельной семьёй. Старый server postCreate-протокол не изменён.
