# Асинхронное ядро языка

Поддерживаются клиентские `Асинх Функция` / `Async Function`,
`Асинх Процедура` / `Async Procedure`, `Ждать` / `Await` и тип
`Обещание` / `Promise`. Корневой standalone-код остаётся клиентским.
Это исполняемое ядро с приостановкой и возобновлением кадров, а не синхронная
обёртка результата. Семейства асинхронных API файлов, сети и интерфейса не добавлены.

```bsl
Асинх Функция ЗначениеПозже(Параметр)
    Возврат Ждать Параметр;
КонецФункции

Асинх Процедура Основная()
    ОбещаниеРезультата = ЗначениеПозже(17);
    Сообщить(Ждать ОбещаниеРезультата);
КонецПроцедуры

Основная();
```

## Исполнение

Вызов начинает выполнять тело сразу, до первого `Ждать` или завершения.
Функция возвращает обещание; процедура не возвращает значение. Даже ожидание
готового обещания или скаляра сохраняет кадр и передаёт управление вызывающему
коду. Возобновления обслуживаются одной FIFO-очередью, без потоков Python и без
одновременного выполнения фрагментов BSL. Обычные вызовы не прокручивают очередь.
Внешняя граница `execute` выполняет готовые продолжения до опустошения очереди.

Число, `Неопределено` и `Null` после `Ждать` сохраняются. Повторное ожидание
обещания возвращает тот же результат или повторно возбуждает его ошибку.
Возвращённое асинхронной функцией обещание усваивается внешним обещанием:
ожидание внешнего получает конечное значение. Все параметры асинхронных
подпрограмм передаются как `Знач`, даже без этого ключевого слова. Переприсваивание
параметра не меняет переменную вызывающего кода; изменение переданного массива
остаётся видимым, поскольку передача по значению не означает глубокое копирование.

Локальные переменные, промежуточные результаты выражений, циклы и обработчики
ошибок сохраняются отдельно для каждого приостановленного задания. Переменные
модуля и экземпляр `ЭтотОбъект` остаются общими для вызовов одного модуля.
Синхронные вызовы и импорты используют текущий динамический контекст задания.
Точность Decimal и профиль native target восстанавливаются на каждой активации.

Ошибки тела асинхронной функции сохраняются в обещании, а не попадают в
`Попытка` вокруг одного вызова. Их перехватывают вокруг `Ждать`. Поля расширенной
ошибки не заменяются общим сообщением. Ошибки вычисления фактических аргументов
и проверки вызова остаются ошибками вызывающего кода. Необработанная ошибка
асинхронной процедуры поступает в отдельный host-канал и выдаётся внешней
границей исполнения, не окружающей процедуру BSL-попыткой. Интерфейс платформенного
показа ошибок не эмулируется.

## Границы и embedding

- `Ждать` разрешён только внутри клиентской асинхронной подпрограммы.
- Асинхронные серверные подпрограммы и перенос обещаний на сервер запрещены.
- `Вычислить` / `Выполнить` не наследуют разрешение на непосредственный `Ждать`
  в строке. Вызов асинхронной функции из динамического кода может вернуть обещание.
- `Ждать` имеет приоритет унарного оператора; для составного операнда используются
  скобки. Полный нативный контракт приоритетов ещё не измерен.
- У обещания нет BSL-конструктора, доступных полей, методов или функции разрешения.
  Строковое представление и сериализация обещаний не поддерживаются.
- `Interpreter.pending_promises` отличает блокировку от завершения;
  `Interpreter.run_until_idle()` обслуживает готовые продолжения. `ensure_complete()`
  отклоняет незавершённый lifecycle, `close()` освобождает приостановленные кадры;
  CLI вызывает их перед успешным завершением и при выходе соответственно. Внутренние
  host-controlled promises используются тестами и не являются новым BSL API.
- Планировщик ограничивает один проход 100000 возобновлениями. Это ограничение
  Yadinassi, не платформы. Оно не прерывает бесконечный код без `Ждать`.
- Ожидание нерешённого обещания без готовых продолжений не считается успешным
  завершением задания. Закрытие/reset отменяет оставшиеся кадры в их контекстах.
- Обещания другого планировщика отклоняются; очередь нельзя прокручивать вложенно.

## Подтверждение и ограничения доказательств

Восемь неизменённых language-only case bodies сопоставлены с принятыми данными
реальной Linux 1С 8.3.27.1508, толстый управляемый клиент файловой базы:
run `39964367396`, commit `5eaa21bb292498a45886f746fb54cc730140ac12`.
Все восемь точных трасс, типизированные значения и структурированные ошибки
повторяются в `tests/test_async_native_observations.py`. Fixtures содержат
provenance и отдельные хеши тела и полного нативного модуля. Это повторное
сопоставление уже полученных данных, не новый нативный запуск.

Подтверждены eager-вызов, порядок изученных ожиданий, повторное ожидание,
скалярные операнды, усвоение внутреннего обещания, значения параметров,
обработка отклонения и смешанные RU/EN ключевые слова. Нативные ошибки сохраняют
измеренные description/code/additional/category/cause. Точные платформенные пути,
строки и private descriptors не переносятся в минимальный standalone wrapper.

Тесты настоящего pending/resume с управляемым host-сигналом проверяют механизм
интерпретатора, но не заменяют нативное доказательство внешнего асинхронного API.
Полная семантика динамического `Ждать`, всех приоритетов, наследования диагностики
между независимыми заданиями и платформенного необработанного procedure-error
остаётся вне нативно подтверждённого среза. Конечные измерения одной Linux-сборки
не являются универсальной спецификацией планировщика Windows/web/mobile.

Исторические функции/коллекции/значения/числа/даты не переписаны; новый fixture
является отдельной семьёй. Старый server postCreate-протокол не изменён.

## Сопоставление восьми случаев в одном запуске

Для отдельного запуска `--client-async-measurement` предусмотрен конечный профиль
`async-language-8-v1`. Он сопоставляет текущий runtime с принятыми нативными
наблюдениями **того же запуска**, а не с ожидаемыми значениями из тестового
fixture. Область профиля ограничена восемью фиксированными language-only телами
для Linux 1С **8.3.27.1508**, толстого управляемого клиента файловой базы.
Это не заявление о совместимости всех асинхронных API или иных клиентов.

Последовательность проверки:

1. Host проверяет нативный отчёт, привязку исходников, завершение нативного
   процесса, транспорт и удаление контейнера. Принятые нативные строки остаются
   только у host.
2. Из закреплённого `scripts/native_1c_bootstrap/full_suite.py` извлекаются
   литералы шаблона и восьми тел через AST, без выполнения Python-кода этого
   файла. Проверяются точные хеши набора тел, шаблона и нативных модулей.
3. Изолированный ограниченный дочерний процесс исполняет текущий подготовленный
   runtime репозитория. Он получает только корень подготовленных исходников,
   **не получает нативных ожидаемых строк**, не читает fixture и не выдаёт
   собственный вердикт о совпадении. Запуск использует `-I`, `-B`, отдельный
   временный cache prefix и ограничения времени, stdout и stderr.
4. Каждый interpreter исполняет точное тело случая с заменой только транспорта,
   capture и корневого запуска, затем закрывается в `finally`. Успешный lifecycle
   требует отсутствия pending-обещаний, удержанных pending-обещаний и флага сбоя.
   Дочерний процесс выдаёт только ограниченные фактические наблюдения.
5. Host строго проверяет форму восьми фактических строк и сравнивает их с
   принятыми строками 1С. Проверяются последовательности событий, типизированные
   слоты и публичные поля ошибок. Для Description, Code и AdditionalInformation
   проверяется точное равенство синтетическим литералам, отдельно проверяются
   категория и причина. Приватный хеш нативного дескриптора не используется как
   ожидаемая ошибка или идентичность объекта.

Перед исполнением и после него проверяется provenance исходников runtime,
включая `scripts/native_async_comparison.py`; отдельно контролируется неизменность
закреплённого источника тел. Несовпадение provenance, неподходящие исходники,
некорректный JSON, неверная схема, превышение лимитов или сбой дочернего процесса
не могут превратиться в успешное сравнение. Приватные пути, текст исключений и
исходные дескрипторы ошибок в результат сравнения не экспортируются.

Новый `probe.async_comparison` содержит профиль, `matched` / `mismatched`, восемь
пар статуса и конечного кода расхождения, а также `actual_sha256`. Этот digest
вычисляет host из канонических **фактических** наблюдений, включая lifecycle и
флаг runtime-сбоя; ожидаемые нативные строки и приватные хеши в него не входят.
Коды расхождения: `trace`, `values`, `errors`, `lifecycle`, `runtimeerror`;
`none` допустим только для совпавшего случая.

Историческое сравнение шести семейств остаётся отдельным `probe.comparison`:
Async-профиль его не заменяет и не ослабляет. `client_async_parity_claimed`
становится истинным только при совпадении всех восьми случаев, принятом
историческом сравнении и выполнении остальных проверок доказательств и очистки.
Поздняя ошибка проверки экспортируемого артефакта снимает заявление о parity.
Корректно оформленное runtime-расхождение делает общий результат неуспешным,
но само по себе не уничтожает уже принятые нативные артефакты: при выполнении
их собственных проверок они сохраняются для диагностики с явным расхождением.
Ошибки целостности, транспорта или очистки не приравниваются к такому расхождению.

Сравнение выполняется только на host: состав входов контейнера и классы
артефактов не расширены. Лимиты остаются прежними: stage wire **8192 байта**,
публичный отчёт и provenance **32768 байт** каждый. Фактический JSON дочернего
процесса ограничен 8192 байтами. Структурная проверка production-сериализаторов
учитывает добавленный результат и все прежние ранние, поздние и ошибочные ветви.

`tests/test_native_async_comparison.py` использует минимальный публичный fixture
из принятого run `39972282106`, commit
`0218f8466f91a46f759cdd9b4e06f72014fa073a`. Вместе с тестами лимитов и защитных
проверок это **offline-регрессия**, не свежее нативное доказательство parity.
Наличие реализации и успешных локальных тестов также не означает, что новый
совместный запуск runtime и реальной 1С уже выполнен и принят.

## Серверные переменные модуля и приостановленный вызывающий код

После объединения с моделью переменных модуля серверная активация по-прежнему
создаётся заново на каждом внешнем переходе клиент → сервер. Сначала полностью
вычисляются фактические аргументы, включая разрешённые `Ждать` в клиентском
Async-коде, затем копируется пакет и выполняются серверные инициализаторы.
Инициализатор видит серверные переменные модуля, но ещё не локальные параметры
вызываемой подпрограммы. Вложенный вызов на той же стороне использует текущую
активацию без повторной инициализации.

Инициализатор остаётся синхронной областью уровня модуля: `Ждать` внутри него
не разрешён. Ошибка инициализации пропускает тело подпрограммы и обратное
копирование параметров; общий `finally` очищает локальное и диагностическое
состояние отделённой активации так же, как при ошибке тела. Приостановленный
клиентский обработчик ошибки и другие задачи не используют это состояние.

Изменение этой границы требует нового совместного нативного сравнения Async8;
доказательство до объединения не заменяет проверку объединённого runtime.
