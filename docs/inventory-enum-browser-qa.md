# Chromium QA для enum inventory

Harness: `tests/browser_ui/inventory_enum_application_browser_qa.mjs`.
Это проверка authored UI-профиля `inventory-enum-forms-v1`, не доказательство
совпадения поведения форм с платформой 1С. Проверка выполняется только через явный opt-in workflow.

## Сценарии и точный бюджет

1. Создание Products и Warehouses через интерфейс, выбор Unit=Piece, сохранение:
   **14 деловых RPC**.
2. Создание Receipt, выбор Warehouse, State=Approved, Product и Unit=Piece в
   строке; Quantity=10.50, Amount=105; Write без движений: **15 RPC**.
3. Post, отображение Movements с текстовыми Piece/Approved, закрытие формы:
   **3 RPC**.
4. Штатное завершение и новый процесс, открытие сохранённого Receipt,
   проверка enum-полей, UndoPosting, пустой Movements, закрытие: **7 RPC**.

5. Создание ещё 50 Warehouses через UI (только обязательный Code), переходы
   между страницами 51 записи, открытие последней, изменение Description,
   сохранение с обновлением второй страницы, поиск, сортировка и Refresh:
   **212 RPC**. Отдельный read-only аудит подтверждает все 51 записи.

Итого **5 сценариев, 251 деловой RPC**. Hello/snapshot и attachment heartbeat
зависят от жизненного цикла клиента: точное общее число заранее не заявляется.
Всего допускается не более 360 RPC; attachment-запросы ограничены отдельно.
Работа ограничена 400 секундами, ещё 20 секунд зарезервированы для очистки.

## Условия запуска

Чистый зафиксированный checkout; `QA_SOURCE_SHA` равен HEAD, `QA_PYTHON`
указывает интерпретатор с зависимостями проекта, `RUNNER_TEMP` является отдельным
доступным абсолютным каталогом. Нужны Linux под обычным пользователем,
Playwright 1.64.1 и его Chromium с рабочим sandbox. Наличие `/usr/bin/chromium`
само по себе не подтверждает наличие браузера, ожидаемого Playwright.
Отключать sandbox, заменять браузер незаявленной версией или обходить проверку
владения процессом нельзя. Невыполненные условия означают блокер, не PASS.

База создаётся свежей и пустой из `examples/configuration-inventory-enum-application`.
Все бизнес-записи создаёт только интерфейс. Python-помощник после создания
выполняет независимые read-only проверки CatalogKey, DocumentKey, EnumKey,
проведённости и движений, сверяя хеш базы до/после чтения. Прямой бизнес-seeding,
инъекции состояния браузера и синтетические RPC не используются.

## Доказательства

Сохраняются пять PNG, `result.json`, `manifest.json` в новом каталоге
`yadinassi-inventory-enum-browser-artifacts` внутри RUNNER_TEMP. Evidence
привязано к commit/tree и хешам исходников; фиксируются фактические RPC и
результаты каждого сценария. Ключи доступа, URL с capability, сырые ошибки,
SQL, содержимое базы и внутренние UUID в артефакты не включаются.
Только новый успешный запуск даёт PASS; статические проверки не заменяют
реальный Chromium-прогон.

## Штатный CI runner

Workflow `.github/workflows/inventory-enum-application-browser-qa.yml`
запускается только при push проверенного снимка в
`codex/inventory-enum-application-browser-reviewed`. Обычные PR и checkpoint
ветки его не запускают. Используются существующие pinned actions, read-only
permissions и свежий непривилегированный Ubuntu runner, без изменения системных
настроек sandbox. Публикуются только перечисленные bounded artifacts.

Локальная попытка на checkpoint `05ccf577` остановилась до запуска Chromium:
окружение не предоставило `/proc/<pid>/task/<pid>/children`, необходимый
проверке владения процессами. Это 0 из 4 сценариев, не доказательство UI PASS.


Ранее run 43202926033 на `b9d1325` подтвердил только первые четыре сценария.
Его PASS не считается проверкой новых страниц: расширенный harness требует
отдельного успешного запуска на объединённом исходном снимке.
