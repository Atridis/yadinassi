# SQLite catalog storage and UUID mapping

Catalog tables and their registry are implemented in SQLite v2. The tabular-section storage extension uses [SQLite v3](sqlite-catalog-sections.md). Configuration/schema evolution remains future work. The logical catalog backend remains separate from this SQLite layout; other backends need not use SQL tables or the same physical names.

## Catalogs and names

Each catalog has its own table with the system columns `record_id`, `revision`, `code`, `description`, and `deletion_mark`, plus one physical column for each supported attribute. For example, a catalog named `Товары` with an attribute `Цена` can use the table `catalog_Товары` and the column `attr_Цена`. Decimal values use exact text, never floating point; typed empty references use SQL NULL internally and remain typed empty references in the backend API. Each single-type reference is constrained to the catalog specified by its metadata; the column stores the referenced record UUID. Composite references are not implemented; when supported they will need an explicit type discriminator, rather than inferring a type from a UUID. Record identity is a stable UUID, scoped in the API by the database and catalog UUID; typed references carry this identity rather than a code or physical name. Do not claim globally unique record UUIDs or exact native empty-reference behavior beyond observed evidence. Code uniqueness applies within one catalog. Existing comparison and ordering semantics stay in the backend until a SQL implementation is proven equivalent.

Physical names are recorded against metadata UUIDs. The design for future configuration updates keeps the name chosen when an object was created stable if its metadata object is renamed later: consequently it can retain an older name. Explicit physical renaming, if provided in the future, must be a separately planned atomic schema migration. A mapping inspection facility must expose the current UUID, logical name and physical name. It must not mutate data.

The SQLite naming implementation must validate and bound names, reserve system namespaces, resolve Unicode-normalization and case collisions deterministically, and retain the chosen mapping. All SQL identifiers are double-quoted and escaped by one audited function; values use parameters. Metadata names are never pasted into SQL as executable fragments. On v2 open, the registry, metadata and complete permitted SQLite schema must be checked against one another, including rejecting unexpected views, triggers and explicit indexes. For compatibility, v1 open permits explicit indexes; the offline migration refuses them rather than silently discarding them. These checks assume a trusted owned directory; they do not defend against a hostile process with the same OS user concurrently replacing files.

## Existing databases and maintenance

Opening a version 1 database does not automatically rewrite it. Migration must be explicit and offline: stop all old processes and prevent their reconnection for the duration and subsequent use. An exclusive SQLite transaction alone cannot stop an already deployed idle version 1 binary from connecting later. Preserve database and metadata UUIDs, record UUIDs, revisions, configuration generation and exact configuration bytes. Existing commit receipts and their canonical intent hash must remain usable without reinterpretation.

A migration should validate the old schema and data before and while streaming records; create all target tables before copying references; verify counts, typed values and referential integrity; and change the version only inside the same transaction. If rollback succeeds before commit, changes are rolled back. If rollback or close fails, the outcome requires recovery and resolution rather than an assumption that the database is unchanged. The caller needs a durable plan identifier and identity/digest persisted before execution; a marker bound to that plan is committed in the same transaction. On an uncertain COMMIT, reopen and verify identity, marker, expected schema and invariants before reporting success. If the evidence is unavailable or mismatched, stop with an uncertain outcome rather than retrying blindly. A separate verified backup and sufficient space for both the new tables and SQLite rollback journal are operational prerequisites. Durability remains subject to the configured journal, synchronization and underlying filesystem.

## Tabular sections: current v3 storage

The [v3 backend contract](sqlite-catalog-sections.md) adds a separate UUID-keyed table for each catalog/section pair, owner FK, UUID rows, explicit ordering and typed attributes. Owner and requested rows share one revision, transaction and receipt. A legacy draft with `tabular_sections=None` leaves rows unchanged; an explicit tuple replaces all section contents and `()` clears them. Deletion marks do not remove owners or rows. Physical deletion of catalog objects remains unsupported; explicit section replacement may remove that owner's old rows inside the same transaction.

The separate [XML/BSL adapter](catalog-tabular-sections.md) supports a bounded metadata and collection profile. UI editing, automatic v2-to-v3 migration and general configuration updates remain unimplemented. Names may change without changing the existing UUID mapping, but altering a real configuration still needs a future explicit migration planner. The fixture rename tests do not provide a production schema-update API.

## Future configuration updates by UUID

Configuration update is not implemented in this storage block. Metadata identity must be the UUID, not the current caption, code or SQL name. Given `(uuid-1, Справочник1), (uuid-2, Справочник2)` followed by `(uuid-1, Справочник2), (uuid-3, Справочник3)`, uuid-1 represents a rename, uuid-2 is removed from the configuration, and uuid-3 is new. A future planner must resolve the complete old and new UUID inventories first, including attributes and tabular sections, and support names being swapped or reused. It must not mistake name reuse for identity or silently attach uuid-2's records to uuid-1 or uuid-3. The existing physical name mapping for uuid-1 can remain stable and readable as its former name; viewing the mapping exposes both names. New UUIDs receive new tables even if their captions match previously used names. No update implementation or automatic data destruction is claimed here. Any future deletion, archival, or structural change affecting stored user data needs an explicit migration plan, safety checks, and authorization appropriate to the operation before it is carried out.

The initial explicit v1 migration supports SQLite's standard UTF-8 database encoding. A manually produced UTF-16 v1 database is refused before committing a schema or data migration; normal v1 opening remains separate. Legacy values that were readable but exceed the old canonical write budget can remain readable after migration and may still be refused on write, as in v1.

Designer can distinguish loading or editing configuration metadata from applying it to the information base. Any future native experiment must explicitly establish whether the changed configuration has been applied before measuring behavior. The internal storage mechanism and number of copies are not assumed here. Yadinassi does not currently implement a two-version Designer workflow; future configuration updates still require a validated migration plan and atomic application, with data-destructive actions separately authorized.
