# Запуск BSL-тестов на реальной 1С

Для изолированного автоматического прогона шести сценариев предусмотрен
[режим Linux/UTC](../docs/native-1c-full-regression.md): новая одноразовая база,
настоящий вывод 1С и побайтовое сравнение с интерпретатором. Он не заменяет
сохранённые Windows-эталоны; публичный отчёт не содержит сырых логов или вывода.
Ниже сохранён самостоятельный ручной launcher для установленной платформы.

## Ручной запуск

```console
python integrational_tests/test_launcher.py --bd "C:\Bases\TestBase" --path-1c "C:\Program Files\1cv8\8.3.27.1859\bin"
```

Скрипт использует только стандартную библиотеку Python 3.10+ и может запускаться
из любой рабочей директории. Пути к тестам, шаблонам и результатам определяются
относительно `test_launcher.py`. Запуск и сбор результатов ручные.

Каталог самодостаточен: его можно целиком скопировать на компьютер с 1С,
без пакета `yadinassi` и корневого каталога `tests`. Python-обвязка отвечает
за генерацию эталонного вывода на реальной 1С. Корневой `tests` предназначен
для проверок yadinassi; в дальнейшем он сможет исполнять эти же `.bsl`
и сравнивать результат с сохраненными файлами `output` без запуска 1С.

## Что требуется на компьютере запуска

- Установленная платформа 1С:Предприятие 8.3 с Конфигуратором и толстым клиентом
  (`1cv8.exe` на Windows или `1cv8` на Linux/macOS). Тонкого клиента недостаточно.
- Существующая файловая база: `--bd` указывает каталог с `1Cv8.1CD`.
  База должна поддерживать управляемое приложение. Скрипт не создает базу
  и не загружает в нее конфигурацию.
- Доступная лицензия 1С и графический сеанс для запуска клиента.
- Пользователь с правами запуска Конфигуратора и открытия внешних обработок.
  Для автоматической работы пользователь тестовой базы должен иметь права
  администратора; защита от опасных действий у него должна быть отключена,
  иначе открытие обработок или файловые операции могут потребовать диалог.
- База должна запускаться без дополнительных диалогов конфигурации, например
  первоначальной настройки или обновления. Открытые сеансы, мешающие запуску
  Конфигуратора, нужно закрыть перед запуском.

`--path-1c` принимает `bin` конкретной версии платформы, каталог версии с `bin`
или macOS `.app`/каталог с `.app`. Скрипт не выбирает версию автоматически
и не использует `1cestart`.

Для учебной платформы с исполняемым файлом `1cv8t` укажите точный путь
через `--executable-1c` вместо `--path-1c`:

```console
python integrational_tests/test_launcher.py --bd "/tmp/test-base" --executable-1c "/точный/путь/1cv8t"
```

Путь к установленному файлу необходимо проверить в выбранном образе или системе.
Скрипт не переименовывает учебный клиент, не подменяет его обычным `1cv8`
и не выбирает редакцию автоматически. Для обоих режимов по-прежнему нужны
Конфигуратор, толстый клиент и существующая тестовая база.

Если у базы есть пользователи:

```console
python integrational_tests/test_launcher.py --bd "C:\Bases\TestBase" --path-1c "C:\Program Files\1cv8\8.3.27.1859\bin" --user "Администратор"
```

Пароль можно передать через переменную окружения `YADINASSI_1C_PASSWORD`
или дополнительный параметр `--password`. Если пользователей нет, достаточно
двух обязательных параметров. `--timeout 300` задает таймаут каждого отдельного
процесса сборки или выполнения (по умолчанию 180 секунд).

## Структура и порядок работы

```text
integrational_tests/
  tests/                  # тематические исходные .bsl
  output/                 # <имя>.out и <имя>.err при ошибках
  launcher_1c/
    Launcher.xml          # обработка запуска с управляемой формой
    Launcher/             # ее форма и модуль
    TestModule.xml        # обработка для подстановки одного теста
    TestModule/Ext/ObjectModule.bsl
  test_launcher.py
  check_launcher.py        # отдельные проверки Python-обвязки с имитацией 1С
  .work/                  # отдельный каталог для каждого запуска, не в Git
```

1. Python находит `.bsl` непосредственно в `tests` и сортирует по имени.
2. В `.work/run-...` копируются шаблоны. Исходные шаблоны не изменяются.
3. Конфигуратор собирает `Launcher.epf` один раз.
4. Для каждого теста его полный текст подставляется в модуль объекта копии
   `TestModule`, затем Конфигуратор собирает отдельный `.epf`.
5. Запускается новый процесс `1cv8 ENTERPRISE /Execute Launcher.epf`.
   В `/C` передается путь к JSON с путями тестовой обработки и файла ответа.
6. Форма запуска в одном серверном вызове очищает очередь сообщений,
   создает объект теста, перехватывает исключение и получает сообщения через
   `ПолучитьСообщенияПользователю(Истина)`. Основной код модуля теста исполняется
   при создании объекта. Объявленные в нем процедуры и функции доступны ему.
7. Форма сохраняет JSON с сообщениями и ошибкой, затем завершает сеанс 1С.
8. Python сохраняет сообщения в `output/<имя>.out`: UTF-8 без BOM,
   переводы строк LF, после каждого сообщения добавляется перевод строки.
   Если сообщений нет, создается файл нулевой длины.

Сборка использует штатный параметр Конфигуратора
`/LoadExternalDataProcessorOrReportFromFiles` с корневым XML-файлом выгрузки.
Проверяются код процесса, `/DumpResult` и наличие непустого `.epf`.
Нулевого кода завершения Предприятия недостаточно: требуется корректный JSON-ответ.

При ошибке исполнения `.out` содержит сообщения, полученные до ошибки,
а `.err` — описание ошибки и путь к логам. При ошибке сборки или обмена
ответом `.out` не создается. Следующие тесты продолжают выполняться.
Предыдущие `.out` и `.err` для найденных тестов удаляются перед прогоном;
результаты удаленных из `tests` тестов автоматически не удаляются.

Коды завершения Python: `0` — все тесты выполнены, `1` — ошибка теста,
сборки или запуска, `2` — неверные аргументы, `130` — прерывание пользователем.
Автоматического сравнения с интерпретатором или эталоном нет: `.out` собираются
для ручной проверки. Логи и сгенерированные обработки остаются в `.work`.

## Формат теста

Файл содержит обычный модуль объекта 1С. Объявления переменных и подпрограмм
должны идти перед основным кодом:

```bsl
Функция Сложить(А, Б)
    Возврат А + Б;
КонецФункции

Процедура Показать(Знач Значение)
    Сообщить(Значение);
КонецПроцедуры

Показать(Сложить(2, 3));
```

Отдельная экспортная процедура `Запустить()` не требуется. Если файл содержит
только определения процедур и функций, основной код ничего не вызовет
и вывод будет пустым. Тест компилируется в серверном контексте модуля объекта;
клиентские функции и директивы модуля управляемой формы здесь не поддерживаются.
Расширения синтаксиса yadinassi, например `# Импорт`, платформа 1С не поддерживает.
Сообщения отдельных фоновых заданий и сообщения, которые тест сам удалил
из очереди, в результат не попадут.

## Проверка шаблонов

Проверки самой Python-обвязки запускаются отдельно, без установленной 1С:

```console
python integrational_tests/check_launcher.py
```

После копирования каталога на другой компьютер можно выполнить
`python check_launcher.py` из него. Эти проверки используют стандартную
библиотеку Python, имитируют ответы платформы и не входят в общий прогон
`python -m unittest discover -s tests`.

XML-шаблоны подготовлены в формате выгрузки Конфигуратора. Здесь проверяется
Python-обвязка с имитацией платформы и корректность XML; реальная сборка и запуск
должны быть проверены на компьютере с установленной 1С. Если конкретная версия
платформы отклоняет шаблон, можно заменить его выгрузкой из этой версии,
сохранив имена объектов и файлов `Launcher`, `Main`, `TestModule`, модуль формы
и структуру каталогов. Для Launcher нужна управляемая форма Main с обработчиком
`ПриОткрытии`, назначенная основной формой; TestModule создается без форм.

Документация: [сборка внешних обработок из файлов](https://edt.1c.ru/dev/edt/2024.2/apidocs/com/_1c/g5/v8/dt/platform/services/core/runtimes/execution/impl/IRuntimeExecutionCommandOptions.html),
[серверные сообщения пользователю](https://1c-dn.com/library/messages_displayed_to_users/),
[модуль объекта и его основной код](https://1c-dn.com/forum/forum23/topic2476/).
